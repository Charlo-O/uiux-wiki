# Product

## Register

product

## Users

uiux.wiki serves AI coding users, independent developers, product managers, founders, junior frontend engineers, designers, and small-team leads who need to name, compare, and implement UI/UX patterns without already knowing the professional vocabulary.

These users usually arrive with natural-language intent such as "a small thing pops up", "make this expand", "show details on hover", or "which component should this be?" Their context is practical: they are preparing prompts, implementation specs, product requirements, or frontend work and want fewer mismatches between intent, design, and code.

## Product Purpose

uiux.wiki is a visual UI/UX glossary and interaction-pattern assistant. It helps users understand components, layouts, styles, motion, states, patterns, and terms, then turns ambiguous interaction descriptions into professional UI patterns, component recommendations, accessibility requirements, and frontend implementation guidance.

Success means a user can quickly find the right UI name, understand when to use it, see a concrete preview, and copy or translate that understanding into a clearer AI coding prompt or frontend specification.

## Brand Personality

Clear, practical, expert.

The product should feel like a compact field guide for interface decisions: direct enough for beginners, precise enough for engineers, and calm enough for repeated reference work.

## Anti-references

Avoid marketing-first SaaS landing pages, decorative hero sections that delay the actual tool, generic AI dashboard styling, modal-first interaction design, hover-only critical content, and visual treatments that make the glossary feel like a sales site instead of a usable reference.

## Design Principles

1. Show the actual UI pattern before explaining it.
2. Keep terminology paired with plain-language meaning.
3. Prefer fast scanning over storytelling.
4. Make component distinctions explicit, especially common confusions such as Dialog vs Drawer vs Popover vs Toast.
5. Treat accessibility, keyboard behavior, focus return, mobile alternatives, and reduced motion as part of the pattern, not as an appendix.

## Accessibility & Inclusion

The interface should support keyboard operation, visible focus, semantic controls, readable contrast, mobile alternatives for hover interactions, and reduced-motion preferences. Patterns involving overlays should communicate escape behavior, focus management, and focus return.
